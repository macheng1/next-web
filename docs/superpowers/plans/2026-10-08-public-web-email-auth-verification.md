## 独立审查与修复

1. Redis keyPrefix 被手工和 ioredis 各加一次，导致验证码无法验证：真实 Redis 复现后修复，写入/验证/消费使用同一业务 key。
2. 注册数据库成功但响应丢失：密码步骤提供登录恢复入口及提示，不重复创建账号。
3. 重置先消费令牌导致密码相同后不能重试：改为领取锁、成功后消费、可恢复失败释放锁；数据库版本仍防止重复更新。
4. 既有登录记录连续 set 丢掉时间和来源：合并为一次数据库更新，新增回归测试。

上述问题均已有失败后通过的针对性验证。独立审查未发现已确认的站外回跳或新凭据越权问题；这不替代真实环境联调。

## 实施裁决

- 使用独立 `(site-auth)` 页面组，避免恢复已退役的历史 `(auth)` 目录；URL 仍为 /login、/register 等。代价：后续维护需按新目录定位。
- 在现有两个开发检出中保留改动，没有创建或合并分支；代价：提交前需按两个仓库分别审阅。
- 额外对注册提交、验证码提交、重置提交、改密和头像操作加共享频控，避免仅限制发信而遗漏高成本请求；代价：高频测试可能触发限流。
- Next.js 流式未登录跳转按浏览器最终到达登录页验收，不把固定 307 状态当作产品行为；后端认证与 API 仍必须明确拒绝未登录请求。
- 认证邮件方法严格判断发送结果，沿用审核类邮件现有行为。找回保留防账号枚举的泛化响应；代价：接口成功不能证明邮件实际送达。
